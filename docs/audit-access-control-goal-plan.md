# 직원별 접근 제어 및 이력관리 GOAL 실행 자료

> 관련 문서: 시스템 전반 검토는 [erp-system-review-checklist.md](erp-system-review-checklist.md), 외부 연동(Popbill)은 [popbill-api-addition-review-checklist.md](popbill-api-addition-review-checklist.md) 참조. 이 문서의 서버 보안 5단계는 ERP 체크리스트 P0 "권한과 보안"과 대응한다.

## GOAL

여러 직원이 함께 사용하는 MESPro에서 누가 어떤 데이터를 등록, 수정, 삭제, 승인했는지 추적하고, 직원별/담당자별/부서별 접근 범위를 적용해 내부 보안을 강화한다.

이 문서는 실제 구현을 끝까지 진행하기 위한 기준 문서다. 구현 중 판단이 흔들릴 때는 아래 원칙, 단계, 완료 기준을 우선한다.

## 핵심 원칙

1. 기준정보는 공용으로 유지한다.
   거래처, 고객사, 제품, 재고 품목 같은 기준정보를 직원별로 분리하면 중복 데이터가 생기고 업무 연결이 깨진다. 대신 수정 권한과 이력 관리를 강화한다.

2. 업무 데이터는 소유자와 담당자를 둔다.
   구매발주, 결제요청, 수금/지급, 품질검사, 고객 클레임, 생산지시, 메모/할 일 등은 작성자, 담당자, 부서, 공유 대상을 기준으로 조회 범위를 제한한다.

3. 화면에서 숨기는 것만으로는 보안이 아니다.
   프론트 권한 제어는 사용성 장치다. 실제 보안은 Firebase Auth, Firestore 보안 규칙, Cloud Functions 같은 서버 측 검증으로 막아야 한다.

4. 모든 중요한 쓰기 동작은 감사 로그를 남긴다.
   등록, 수정, 삭제, 복구, 상태 변경, 승인, 반려, 일괄 처리, 엑셀 붙여넣기, Drive 저장, PDF/엑셀 내보내기 같은 동작은 누가 언제 했는지 남긴다.

## 현재 코드에서 확인된 출발점

- 역할 기반 권한 관리가 이미 존재한다.
  - `src/js/rbac.js`
  - `src/js/cloud-sync.js`
  - 시스템 관리의 권한 관리 화면

- 일부 이력은 이미 존재한다.
  - 재무 변경 이력: `financeData.auditLog`
  - 재고 입출고 이력: `inventoryLedger`
  - 메모/할 일 수정 이력

- 현재 한계
  - 이력 형식이 모듈별로 다르다.
  - 등록자/수정자 필드가 모든 데이터에 일관되게 붙어 있지 않다.
  - 직원별 데이터 접근 제한은 화면 중심이고, 저장소 단계의 강한 보안은 별도 설계가 필요하다.
  - 일괄 등록/일괄 수정 시 개별 항목별 이력이 충분히 남는지 점검이 필요하다.

## 권장 데이터 모델

모든 주요 업무 데이터에 아래 필드를 공통으로 추가한다.

```js
{
  createdBy: "userId",
  createdByName: "홍길동",
  createdAt: "2026-06-26T10:30:00.000Z",
  updatedBy: "userId",
  updatedByName: "김영희",
  updatedAt: "2026-06-26T11:10:00.000Z",
  ownerUserId: "담당자 userId",
  ownerDeptId: "생산팀",
  visibility: "private | assignee | department | shared | company",
  sharedWith: ["userId1", "userId2"],
  approvalUsers: ["userId3"],
  deletedBy: "",
  deletedAt: "",
  restoredBy: "",
  restoredAt: ""
}
```

별도 감사 로그는 아래처럼 표준화한다.

```js
{
  id: "AUD-...",
  entityType: "purchaseOrder | paymentRequest | inventory | claim",
  entityId: "PO-260626-0001",
  action: "create | update | statusChange | delete | restore | approve | reject | bulkUpdate | export",
  actorUserId: "userId",
  actorName: "홍길동",
  actorRole: "manager",
  at: "2026-06-26T11:10:00.000Z",
  summary: "단가 변경",
  changes: [
    { field: "unitPrice", before: 10000, after: 12000 }
  ],
  reason: "공급처 단가 인상",
  source: "ui | excelPaste | bulkAction | cloudSync"
}
```

## 접근 범위 정책

| 범위 | 의미 | 예시 |
| --- | --- | --- |
| `private` | 작성자만 조회 | 개인 메모, 개인 할 일 |
| `assignee` | 작성자와 담당자만 조회 | 결제요청, 고객 클레임 |
| `department` | 작성자, 담당자, 같은 부서 조회 | 생산지시, 품질검사 |
| `shared` | 지정된 직원만 추가 조회 | 특정 프로젝트성 문서 |
| `company` | 회사 공용 조회 | 거래처, 제품, 재고 기준정보 |

관리자는 전체 조회가 가능하고, 최상위 관리자는 권한 변경 및 감사 로그 전체 조회가 가능해야 한다.

## 항목별 권장 정책

| 항목 | 조회 권한 | 수정 권한 | 이력 중요도 |
| --- | --- | --- | --- |
| 구매발주서 | 작성자, 구매 담당자, 결재자, 관리자 | 작성자/구매 담당자, 승인 후 제한 | 매우 높음 |
| 결제요청 | 요청자, 결제 담당자, 관리자 | 요청자/결제 담당자, 지급완료 후 제한 | 매우 높음 |
| 수금/지급 | 재무 담당자, 관리자 | 재무 담당자, 월 마감 후 제한 | 매우 높음 |
| 고정비 | 재무 담당자, 관리자 | 재무 담당자 | 높음 |
| 재고 | 담당 부서, 관리자 | 재고 담당자, 관리자 | 매우 높음 |
| 생산지시 | 생산 부서, 담당자, 관리자 | 생산 담당자, 관리자 | 높음 |
| 품질검사 | 품질 부서, 담당자, 관리자 | 품질 담당자, 관리자 | 높음 |
| 고객 클레임 | 등록자, 담당자, 품질/영업 관리자 | 담당자, 관리자 | 매우 높음 |
| 메모/할 일 | 개인 기본, 공유 가능 | 작성자/공유 권한자 | 중간 |
| 거래처/고객사/제품 | 공용 조회 | 권한 있는 직원만 수정 | 높음 |

## 구현 단계

### 1단계: 현재 사용자 식별 통일

목표는 모든 등록/수정 함수에서 현재 사용자를 안정적으로 가져오는 것이다.

- `getCurrentActor()` 유틸 추가
- 로그인 사용자 ID, 이름, 이메일, 역할, 부서 반환
- 로컬/미인증 모드에서는 `local-admin` 같은 안전한 기본값 사용

완료 기준:
- 모든 새 이력 로그가 동일한 사용자 구조를 사용한다.
- 로그인하지 않은 상태에서도 오류 없이 기록된다.

### 2단계: 감사 로그 표준화

모듈별 이력을 하나의 공통 함수로 남긴다.

- `writeAuditLog(entityType, entityId, action, before, after, options)`
- 변경 전/후 비교 함수 추가
- 일괄 처리 시 대표 로그 + 개별 로그 정책 결정
- 시스템 관리에 감사 로그 조회 화면 추가

우선 적용 대상:
1. 구매발주서
2. 결제요청
3. 수금/지급
4. 고정비
5. 재고
6. 고객 클레임

완료 기준:
- 각 대상에서 등록/수정/삭제/상태변경 로그가 남는다.
- 로그에서 사용자, 시간, 항목, 변경 전/후 값을 확인할 수 있다.

### 3단계: 데이터 소유권 필드 추가

기존 데이터에 아래 필드를 점진적으로 채운다.

- `createdBy`
- `updatedBy`
- `ownerUserId`
- `ownerDeptId`
- `visibility`
- `sharedWith`

마이그레이션 원칙:
- 기존 데이터는 기본적으로 `company` 또는 관리자 소유로 시작한다.
- 업무 데이터는 가능한 경우 기존 담당자명/작성자 정보를 기반으로 매핑한다.
- 매핑할 수 없는 데이터는 관리자 검토 목록에 표시한다.

완료 기준:
- 신규 등록 데이터에는 소유권 필드가 자동으로 들어간다.
- 기존 데이터도 최소 기본값을 갖는다.

### 4단계: 화면 접근 제어

현재 RBAC 위에 데이터 단위 필터를 추가한다.

- `canViewRecord(record, entityType)`
- `canEditRecord(record, entityType)`
- `canDeleteRecord(record, entityType)`
- `canApproveRecord(record, entityType)`

화면 규칙:
- 조회 권한 없는 행은 목록에서 보이지 않음
- 보기 가능하지만 수정 불가인 행은 버튼/선택바 동작 비활성
- 삭제/복구/내보내기는 별도 권한 확인

완료 기준:
- A직원 private 데이터가 B직원 목록에 보이지 않는다.
- 담당자로 지정된 데이터는 작성자가 아니어도 볼 수 있다.
- 관리자는 전체 데이터 접근 가능하다.

### 5단계: 서버 측 보안 강화

강한 보안을 위해 Firestore 보안 규칙 또는 Cloud Functions 기반 쓰기 API로 전환한다.

권장 방식:
- 클라이언트는 직접 전체 데이터 쓰기를 줄인다.
- 민감한 쓰기 동작은 Cloud Functions에서 사용자 권한 확인 후 처리한다.
- Firestore Rules에서 사용자별/역할별 읽기 범위를 제한한다.

완료 기준:
- 브라우저 콘솔이나 SDK 직접 호출로도 타인의 private 데이터를 읽을 수 없다.
- 관리자 외 권한 변경이 불가능하다.

### 6단계: 이력 UI와 알림

- 각 문서 상세에 `이력` 버튼 추가
- 타임라인 형태로 변경 이력 표시
- 변경 전/후 값 강조
- 중요 항목 변경 시 사유 입력
- 담당자에게 알림 생성

완료 기준:
- 구매발주서나 결제요청에서 이력 버튼을 눌러 변경 내역을 확인할 수 있다.
- 단가, 수량, 지급상태, 재고수량 변경은 변경 사유를 남길 수 있다.

## 검증 체크리스트

### 이력 검증

- [ ] 신규 구매발주서 등록 시 등록자/등록일시가 남는다.
- [ ] 구매발주서 수량 변경 시 변경 전/후 값이 남는다.
- [ ] 결제요청 상태 변경 시 변경자와 시간이 남는다.
- [ ] 수금/지급 처리 시 처리자와 처리금액이 남는다.
- [ ] 재고 조정 시 조정 전/후 수량이 남는다.
- [ ] 삭제 후 휴지통 복구 시 삭제자/복구자가 남는다.

### 권한 검증

- [ ] A직원 private 데이터가 B직원에게 보이지 않는다.
- [ ] 담당자로 지정된 직원은 해당 데이터를 볼 수 있다.
- [ ] 같은 부서 공유 데이터는 부서원이 볼 수 있다.
- [ ] 일반 직원은 관리자 권한 화면에 접근할 수 없다.
- [ ] 관리자와 최상위 관리자는 전체 데이터와 감사 로그를 볼 수 있다.
- [ ] 보기 전용 권한자는 수정/삭제/상태 변경을 할 수 없다.

### 서버 보안 검증

- [ ] Firestore Rules 또는 Functions에서 권한 없는 읽기를 차단한다.
- [ ] 권한 없는 쓰기를 차단한다.
- [ ] 감사 로그는 일반 사용자가 수정/삭제할 수 없다.
- [ ] 권한 변경은 최상위 관리자만 가능하다.

## GOAL 진행 시 작업 단위

GOAL을 이어서 진행할 때는 한 번에 전부 바꾸지 말고 아래 단위로 끊는다.

### GOAL 1: 감사 로그 기반 만들기

산출물:
- 현재 사용자 유틸
- 공통 감사 로그 유틸
- 감사 로그 데이터 구조
- 시스템 관리 감사 로그 기본 조회 화면

완료 기준:
- 임의 테스트 로그를 남기고 화면에서 조회 가능하다.

### GOAL 2: 재무/구매 핵심 이력 적용

산출물:
- 구매발주서 등록/수정/삭제/상태변경 이력
- 결제요청 등록/수정/상태변경/삭제 이력
- 수금/지급 처리/복원 이력
- 고정비 등록/월별수정/삭제 이력

완료 기준:
- 돈과 결제 관련 변경은 모두 사용자와 변경 전/후 값이 남는다.

### GOAL 3: 재고/품질/클레임 이력 적용

산출물:
- 재고 입출고/조정 이력 표준화
- 생산지시 상태 변경 이력
- 품질검사 결과 변경 이력
- 고객 클레임 담당자/상태 변경 이력

완료 기준:
- 품목, 수량, 상태, 담당자 변경 추적이 가능하다.

### GOAL 4: 데이터 접근 제어 적용

산출물:
- `visibility`, `ownerUserId`, `ownerDeptId`, `sharedWith` 필드 적용
- 목록 필터링
- 수정/삭제/승인 권한 체크

완료 기준:
- 직원별/담당자별/부서별 데이터 노출 범위가 다르게 동작한다.

### GOAL 5: 서버 보안 규칙 적용

산출물:
- Firestore Rules 또는 Functions 기반 권한 검증
- 감사 로그 쓰기 보호
- 권한 없는 접근 차단 테스트

완료 기준:
- 화면 조작이 아니라 저장소 단계에서 타인 데이터 접근이 차단된다.

## 주의할 점

- 직원별로 기준정보를 복제하지 않는다.
- 관리자 화면만 숨기는 것으로 보안을 완료했다고 판단하지 않는다.
- 모든 데이터를 private으로 시작하면 업무 협업이 막힌다.
- 결재/승인 완료, 월 마감, 지급완료 이후에는 수정 제한이 필요하다.
- 일괄 수정은 반드시 요약 로그와 개별 변경 로그를 함께 남길지 결정해야 한다.

## 최종 완료 정의

아래 조건을 만족하면 이 GOAL은 완료로 본다.

- 주요 업무 데이터에 등록자/수정자/담당자/접근 범위가 저장된다.
- 주요 변경 동작이 감사 로그로 남는다.
- 각 화면에서 권한 없는 데이터가 보이지 않는다.
- 보기 전용 사용자는 수정/삭제/상태변경을 할 수 없다.
- 관리자와 최상위 관리자는 감사 로그를 조회할 수 있다.
- 서버 측 보안 규칙 또는 Functions 검증으로 타인 데이터 접근이 차단된다.
- 실제 사용자 시나리오로 A직원/B직원/관리자 테스트를 통과한다.
