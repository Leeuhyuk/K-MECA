#### 판정

- [x] **전면 개편은 권장한다.** 다만 한 번에 화면을 교체하는 방식이 아니라 `업무 규칙 안정화 -> 디자인 시스템/앱 셸 -> 핵심 업무 흐름 -> 나머지 도메인` 순서의 단계적 React 전환으로 진행한다.
- [x] 목표는 장식이 많은 SaaS 화면이 아니라 **조용하고 정밀한 제조·운영용 인터페이스**다. 한 화면에서 비교·선택·처리하는 현재 ERP의 정보 밀도는 유지한다.
- [x] 현재 범위는 레거시 HTML 18개 약 1,757줄, JavaScript 39개 약 27,260줄, CSS 4개 약 5,006줄이며 React 소스는 17개 약 1,487줄이다. 따라서 CSS만 교체하면 구조적 문제가 남고, 전면 일괄 재작성은 업무 회귀 위험이 크다.

#### 방식 비교

| 방식 | 장점 | 위험 | 판정 |
|---|---|---|---|
| 외형만 현대화 | 빠르고 초기 비용이 작음 | 중복 DOM, 전역 상태, 접근성, 모바일 분리 문제가 그대로 남음 | 임시 개선에만 사용 |
| 업무 흐름별 React 전환 | 운영을 유지하면서 공통 UI와 상태 소유권을 정리 가능 | 과도기 호환 계층 관리가 필요 | **권장** |
| 전체 일괄 재작성 | 최종 구조가 가장 깔끔할 수 있음 | 누락된 업무 규칙과 데이터 회귀를 한 번에 발견하게 됨 | 권장하지 않음 |

#### 현대적 디자인 목표

- [ ] 앱 셸은 접을 수 있는 좌측 내비게이션, 52~56px 상단 바, 고정 필터 바, 스크롤 가능한 데이터 영역으로 통일한다.
- [ ] 화면 제목은 18~20px, 본문·표는 13~14px, 메타데이터는 최소 12px로 사용하고 숫자는 우측 정렬과 tabular 숫자를 적용한다.
- [ ] 흰색·중성 회색 작업면을 중심으로 파랑은 정보/선택, 청록은 대표 실행, 초록·주황·빨강은 상태 의미에만 제한한다.
- [ ] 그림자는 드롭다운·팝오버·드로어처럼 떠 있는 레이어에만 사용하고 일반 섹션은 선과 간격으로 구분한다.
- [ ] 테이블은 체크박스/핵심 식별 열 고정, 행 높이 40~44px, 정렬·열 표시·저장 보기·빈 상태·로딩 상태를 공통 제공한다.
- [ ] 상세 드로어는 읽기, 수정, 이력, 문서 작업을 탭 또는 명확한 구역으로 묶고 대표 작업 한 개만 강조한다.
- [ ] 등록 드로어는 단건 420~480px, 다중 품목 760~900px를 사용하며 검증 오류를 필드와 상단 요약에서 함께 보여준다.
- [ ] 데스크톱과 모바일은 같은 데이터를 사용하되 작업 도구를 별도 컴포넌트로 렌더한다. 모바일은 하단 내비게이션, 전체 화면 등록, 선택 작업 더보기 메뉴를 사용한다.
- [ ] `lucide-react` 등 하나의 아이콘 체계를 사용하고 아이콘 단독 버튼에는 툴팁과 접근 가능한 이름을 제공한다.
- [ ] 미세한 120~180ms 전환만 사용하고 `prefers-reduced-motion`을 지원한다.

#### 권장 정보 구조

- [ ] 1차 내비게이션을 `홈`, `영업`, `구매`, `생산`, `재고`, `품질`, `재무`, `기준정보`, `시스템`으로 재분류한다.
- [ ] 자주 쓰는 화면과 최근 화면을 상단에 제공하고 긴 사이드바의 하위 그룹은 한 번에 하나만 펼치거나 사용자가 고정할 수 있게 한다.
- [ ] 목록 화면의 기본 흐름을 `제목/요약 -> 필터/검색 -> 선택 작업 -> 표 -> 우측 상세`로 고정한다.
- [ ] 대시보드는 총계 카드 나열보다 `오늘 처리할 일`, `지연`, `재고 부족`, `승인 대기`, `연동 실패`를 우선한다.
- [ ] 문서 처리(PDF, Excel, 이메일, Drive)는 각 상세 화면의 공통 `문서 처리` 메뉴로 통합한다.

#### 기술 구조

- [ ] React 앱 셸과 라우터를 먼저 만들고 각 도메인을 독립 경로와 기능 단위로 마운트한다.
- [ ] `tokens -> primitives -> shared patterns -> domain screens`의 4단계 컴포넌트 구조를 사용한다.
- [ ] 서버/로컬 저장 접근을 UI에서 분리하고 조회·명령·검증·상태 전이를 도메인 서비스로 이동한다.
- [ ] React Query 또는 동등한 서버 상태 계층을 도입할 때 현재 전역 배열과 이중 소유하지 않도록 도메인별 전환 시점에 한 번에 소유권을 넘긴다.
- [ ] Storybook 또는 독립 컴포넌트 카탈로그에서 버튼, 입력, 상태, 표, 드로어, 확인창의 모든 상태를 검증한다.
- [ ] 시각 회귀 테스트를 데스크톱 1440px, 소형 노트북 1280px, 태블릿, 모바일 390px 기준으로 추가한다.

#### 단계별 전환안

1. **기반 안정화**: P0 보안·재고 무결성, 핵심 업무 규칙, E2E 기준 시나리오를 고정한다.
2. **디자인 기반**: 토큰, 공통 컴포넌트, 앱 셸, 내비게이션, 드로어, 표, 폼, 알림을 구축한다.
3. **핵심 흐름**: 재고·자재 -> 견적요청·구매발주 -> 수주·납품을 업무 흐름 단위로 전환한다.
4. **확장 흐름**: 생산·품질 -> 재무·인사 -> 기준정보·시스템 순으로 전환한다.
5. **레거시 제거**: 전역 브리지, `LegacyTableIsland`, 숨겨진 원본 DOM, 사용하지 않는 CSS/함수를 제거한다.

#### 완료 기준

- [ ] 기존 핵심 E2E 시나리오가 모두 통과하고 레거시 대비 데이터 결과가 일치한다.
- [ ] 키보드만으로 목록 선택, 검색, 등록, 수정, 저장, 닫기를 수행할 수 있다.
- [ ] 200% 확대와 390px 모바일에서 본문 겹침 없이 대표 작업을 완료할 수 있다.
- [ ] 화면별 임의 CSS 대신 공통 토큰과 컴포넌트 사용률을 추적하고 레거시 CSS 감소량을 확인한다.
- [ ] 등록·수정 실패율, 업무 완료 시간, 사용자 오입력, 지원 문의를 개편 전후로 비교한다.
